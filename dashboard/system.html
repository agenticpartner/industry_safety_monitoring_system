What this is

A 20-camera industrial safety pipeline running entirely on one Jetson AGX Orin: PPE and fire/smoke detection on every stream, zone analytics, a vision-language model that reviews each incident, and a language model that answers questions about them. Nothing leaves the device except the alerts you choose to send.

DLA is unused, deliberately. A model is placed on DLA only if it compiles without --allowGPUFallback. A graph split between DLA and GPU ping-pongs tensors at every subgraph boundary and is typically slower than pure GPU while appearing to "use DLA". Neither detector qualifies, so both run on the GPU.

Decode ceiling contradicts the datasheet

NVDEC saturates and then divides its fixed capacity among however many streams ask for it — so the ceiling is a throughput number, not a stream count.

MeasurementValue

Implied concurrent streams~36

The datasheet's 22 is a conservative product-spec figure; measured throughput on this JetPack 7.2 / L4T R39.2 build is higher. The demo still uses 20 because the GPU, not the decoder, is the real limit — at 20 streams NVDEC sits well inside its ceiling while the GPU is at 99%. H.265 is not optional: H.264 has a materially lower ceiling and will not hold 20 streams.

Pipeline

One DeepStream graph, built with pyservicemaker. Detection runs batched across all cameras; everything after the tracker is per-frame metadata work.

The dashed path is the cold path: the probe publishes state transitions fire-and-forget to Redis and never blocks the graph. Measured cost of publishing at 20 streams: −0.9% (514.2 → 509.6 fps), zero drops. The queue is bounded and drops oldest-first, so an unavailable consumer cannot slow or stall the graph. To watch live work move along these edges, open /flow — this page stays a measured reference.

Both run at infer-dims 3;640;640. The parser and cluster-mode must match the head: PPE is pre-NMS → NvDsInferParseYoloPreNMS + cluster-mode 2 (DeepStream runs NMS); fire is post-NMS → NvDsInferParseYoloPostNMS + cluster-mode 4 (no clustering). Mismatch them and boxes are silently wrong rather than absent.

FP16 ships, not INT8. INT8 is 1.44× faster on paper, but the pipeline is not inference-bound at 20 streams — the GPU is saturated by the whole graph — so the extra throughput buys nothing while costing calibration and accuracy risk.

Live RTSP cameras

The capacity table above is file mode, run flat out — that is what measures the ceiling. Live sources are paced by the cameras, so throughput can never exceed realtime and the useful question becomes whether the box keeps up. Measured on 20 cameras served over the LAN.

The gap is ingest, not compute. With 70% of the GPU idle the pipeline cannot be the constraint. Twenty concurrent TCP RTSP streams arrive from a single host over one NIC, and nvstreammux in live-source mode batches on a 40 ms timeout without waiting for stragglers — so jittered frames miss their batch. Real cameras are independent devices with their own uplinks; the same footage in file mode runs at 484 fps on this box. Treat ~190 fps as a property of the demo rig, not of the Jetson.

Serving requirements. Cosmos Reason 2 is a Qwen3-VL architecture and needs --image-min-tokens 1024: below that floor it stops grounding on the image and answers from the prompt. The mmproj projector is mandatory — the model loads and responds without it, but is blind.
Perception, not judgement. The model is asked only what is visible — is the subject a person, is a vest present, how many people, is there fire or smoke — and the verdict is computed from those answers against the zone's configured limits. Asking a VLM for the verdict directly yields fluent, self-contradictory reasoning; a schema constrains shape but not coherence.

/no_think is required. Nemotron Nano v2 is a reasoning model and its thinking tokens count against max_tokens. The OpenAI-style chat_template_kwargs.thinking and reasoning_effort switches are silently ignored by this build.
Grammar-constrained decoding. Tool selection and the final answer are both emitted under a JSON schema, so the model cannot name a camera or zone that does not exist — the enums are built from the live database at request time. Free-text fields carry explicit length bounds: an unbounded string under a grammar has no reason to terminate and will generate to the token ceiling.
llama.cpp, not vLLM. Both work on JetPack 7. llama.cpp costs the hot path 3.3% vs vLLM's 12.9%, and 14.8 GB peak RAM vs 40.3 GB. vLLM is faster per request (TTFT 0.05 s vs 0.12 s idle) and remains the better choice if reasoning ever moves onto the hot path. Two resident models cost nothing when idle — 517.8 fps at 20 streams with both loaded, identical to baseline. Only inference competes.

Latency, end to end

File sources (left) and live RTSP cameras (right). The two differ mainly in how evidence is captured, and that difference propagates into every clock downstream.

Stagefile p50RTSP p50RTSP p90What it covers
Detection → alert visible0.27 s0.12 s0.19 s rule fires → Redis → store → queryable
Evidence clip ready2.11 s11.09 s12.18 s ffmpeg stream-copy · vs smart record
VLM verdict12.49 s22.93 s69.96 s waits for the clip, then queues
VLM inference alone~6.7 s per call (5.6–8.9 s), serial crop + inference + decision
Agent answer11.2 s idle · 23.8 s at 20 streams plan + retrieve + synthesise
Why the clip is slower over RTSP, and why that is not a regression. A file source is already on disk, so the window can be cut the moment the incident lands. A live camera has to be recorded: smart record dumps pre_roll + post_roll from its ring buffer, so the file cannot exist until that window has physically elapsed. The VLM clock inherits the wait — 22.9 s p50 is 11 s of clip plus queueing, against 6.7 s of actual inference. The p90 of 70 s is a cold-start burst, not steady state.
The alert is instant; the adjudication is not. An incident appears in under a second marked unverified and its verdict lands later. Adjudication is serial by design — one VLM request in flight is what keeps its hot-path cost at 3.3% — so a burst queues: ~31 incidents arriving in 40 s take ~3.5 minutes to fully adjudicate. In steady state incidents arrive as transitions, at a rate the adjudicator absorbs comfortably.

Services poll the store rather than being called by the pipeline. Each is independently restartable and naturally rate-limited, and a failure in any of them — a stalled model server, an unreachable network — cannot touch incident capture. The store is WAL and opened read-only for queries, so the dashboard reads while 20 cameras write.

Data flow

detector → rules (debounce) → state TRANSITION → Redis → incident store → clip → VLM verdict → dashboard / Telegram / agent

An event is a state transition, not a frame observation. The rules layer publishes only when a debounced verdict flips — 2225 frame-level observations across 6 cameras in 120 s resolve to 6 incidents. Incidents are reference-counted: one incident folds many tracks and closes only when the last of them clears, so track-id churn does not fragment a single situation into dozens of rows.
